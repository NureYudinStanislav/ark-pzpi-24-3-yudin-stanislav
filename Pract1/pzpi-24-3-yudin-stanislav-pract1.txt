3 ОПИС ВИКОНАНОЇ РОБОТИ
     Go (Golang) – це сучасна компільована статично типізована мова програмування з відкритим кодом, розроблена інженерами компанії Google (Робертом Грізміром, Робом Пайком та Кеном Томпсоном) і представлена у 2009 році. Метою створення Go було поєднання високої продуктивності й типобезпеки C/C++ зі швидкістю компіляції, простотою розробки та зручністю скриптових мов на кшталт Python.
     Ключовими відмінностями філософії Go є максимальний мінімалізм синтаксису, вбудована підтримка конкурентності (горутини goroutines та канали channels), інтерфейси з неявною типізацією (duck typing) без класичного успадкування класів, а також автоматичне форматування вихідного коду за єдиним загальноприйнятим стандартом [1].
     У командній розробці дотримання єдиного стандарту коду знижує витрати на код-рев'ю, прискорює онбординг нових інженерів та мінімізує дефекти, викликані нерозумінням логіки колег. Go спочатку проектувався з акцентом на простоту читання: код читається значно частіше, ніж пишеться. Уніфікація стилю через інструменти мови гарантує, що програми, написані різними інженерами, виглядають так, ніби їх створив один автор.
     3.1 Структура проєкту та коду
     3.1.1 Рекомендація: Дотримуйтесь стандартної структури каталогів (Standard Go Project Layout)   
     Go-проєкти не повинні складати всі файли в кореневу папку. Ідіоматичний підхід передбачає чітке розділення:
        ­ /cmd/ – точки входу в програму (файли main.go для кожного бінарника);
        ­ /internal/ – приватний код програми, який заборонено імпортувати іншим зовнішнім модулям (гарантується компілятором Go);
        ­ /pkg/ – публічні бібліотеки та утиліти, призначені для перевикористання сторонніми проектами [2].
     Чому важливо: чітка структура каталогів запобігає заплутуванню циклічних імпортів (import cycle not allowed) та захищає внутрішні API сервісу від несанкціонованого зв'язування зовнішніми споживачами.   
     Наслідки недотримання: хаотичне розташування файлів призводить до монолітних пакетів, виникнення циклічних залежностей та втрати контролю над публічним контрактом додатку.
     Вплив на підтримку: дозволяє новому розробнику миттєво зрозуміти, де починається запуск додатку, а де зосереджена доменна логіка.
     3.1.2 Рекомендація: Групуйте імпорти на стандартизовані блоки   
     Імпорти повинні бути відсортовані та розбиті порожнім рядком на 2 або 3 логічні групи: 
     1) пакети стандартної бібліотеки Go; 
     2) сторонні бібліотеки (third-party); 
     3) внутрішні пакети поточного проекту. Заборонено змішувати їх у загальну купу.
     Приклад:
      // Поганий приклад (хаотичний імпорт без розділення)
      import (
      	"myproject/internal/user"
      	"fmt"
      	"github.com/google/uuid"
      	"os"
      )
      
      // Гарний приклад (групування за джерелом)
      import (
      	// 1. Стандартна бібліотека
      	"fmt"
      	"os"
      
      	// 2. Сторонні бібліотеки
      	"github.com/google/uuid"
      
      	// 3. Внутрішні пакети проекту
      	"myproject/internal/user"
      )
     
     Чому важливо: чітке розмежування імпортів дозволяє з першого погляду оцінити залежності модуля, відділяючи надійні вбудовані засоби мови від зовнішніх бібліотек та внутрішніх пакетів сервісу. Такий порядок є офіційною рекомендацією спільноти Go та автоматично підтримується стандартною утилітою goimports.
     Наслідки недотримання: хаотичне розташування імпортів уповільнює навігацію файлом, ускладнює виявлення небажаних зовнішніх залежностей на етапі код-рев'ю та призводить до частих конфліктів злиття (merge conflicts) у системі контролю версій Git, оскільки автоматичні форматтери постійно переставлятимуть рядки місцями.
     Вплив на підтримку: інженер миттєво розуміє архітектурну зв'язаність файлу: наскільки він спирається на базову мову, які сторонні фреймворки використовує та з якими локальними підсистемами взаємодіє, що суттєво полегшує аудит залежностей та оновлення модуля.
     3.2 Форматування та стиль
     3.2.1 Рекомендація: Завжди форматуйте код за допомогою утиліти gofmt (табуляція для відступів)
     У спільноті Go не існує дискусій щодо пробілів і стилю фігурних дужок. Увесь код повинен автоматично форматуватися офіційною утилітою gofmt (або goimports). Відступи виконуються виключно символом табуляції (\t), відкриваюча фігурна дужка обов'язково залишається на тому ж рядку, де й оператор.
     Приклад:
      // Поганий приклад (використання пробілів для відступів, дужка на новому рядку)
      func CalculateSum(a int, b int) int
      {
          return a + b
      }
      
      // Гарний приклад (відформатовано gofmt: табуляція, єдиний стиль дужок)
      func CalculateSum(a int, b int) int {
      	return a + b
      }
     
     Чому важливо: gofmt усуває суперечки про стиль коду в команді і забезпечує 100% консистентність будь-якого проекту в екосистемі Go.
     Наслідки недотримання: код не пройде перевірку лінтерами в CI/CD; відкриваюча дужка на новому рядку взагалі викличе помилку компіляції через автоматичну розстановку крапки з комою компілятором Go (Semicolon Insertion Rule).
     Вплив на підтримку: розробники зосереджуються на архітектурі та бізнес-логіці, а не на візуальних правилах оформлення.
     3.3 Правила іменування
     3.3.1 Рекомендація: Використовуйте camelCase / PascalCase замість snake_case та враховуйте видимість через регістр
     Go не використовує ключові слова на кшталт public або private. Видимість (експорт) елемента за межі пакета визначається виключно першою літерою: з великої літери (PascalCase) – експортований (публічний), з малої літери (camelCase) – приватний. snake_case суворо не рекомендується.
     Приклад:
      // Поганий приклад (використання snake_case)
      type user_account struct {
      	user_name string
      	user_age  int
      }
      
      func get_user_data() {}
      
      // Гарний приклад (PascalCase для експортованих, camelCase для внутрішніх)
      type UserAccount struct {
      	UserName string // експортоване поле (доступне ззовні)
      	userAge  int    // неекспортоване поле (приватне для пакета)
      }
      
      func getUserData() {} // неекспортована функція

     Чому важливо: регістр першої літери безпосередньо впливає на компіляцію та публічний API бібліотеки.
     Наслідки недотримання: випадкове використання великої літери розкриває внутрішній стан типу назовні, а мале ім'я робить тип недоступним для зовнішніх пакетів.
     Вплив на підтримку: дозволяє з першого погляду на виклик зрозуміти область видимості та контракт сутності.
     3.3.2 Рекомендація: Зберігайте акроніми та абревіатури в єдиному регістрі
     Акроніми, ініціалізми та абревіатури (наприклад, URL, HTTP, ID, JSON, API) повинні бути повністю у верхньому регістрі (якщо експортовані або всередині назви) або повністю в нижньому (якщо починають приватне ім'я). Не використовуйте форми на кшталт HttpServer або JsonParser.
     Приклад:
      // Поганий приклад (змішаний регістр абревіатур)
      type JsonParser struct{}
      var userId string
      func ServeHttp() {}
      
      // Гарний приклад (акронім зберігає суцільний регістр)
      type JSONParser struct{}
      var userID string
      func ServeHTTP() {}
      var rawURL string
     
     Чому важливо: це офіційне правило Go Code Review Comments [3], яке запобігає безладу в іменуванні загальновідомих протоколів і форматів.
     Наслідки недотримання: виникає плутанина під час автодоповнення (розробник не знає, шукати Json чи JSON).
     Вплив на підтримку: стандартизоване найменування скорочень покращує якість автогенерації клієнтів та документації.
     3.3.3 Рекомендація: Прагніть до лаконічності імен у вузьких областях видимості та уникайте надлишковості
     Довжина імені змінної в Go повинна бути пропорційною розміру її області видимості. Для локальних циклів прийнятні однолітерні назви (i, v, k). Також слід уникати тавтології: назва пакета вже визначає контекст, тому дублювати її в іменах типів чи функцій заборонено (user.User – погано, user.Account – добре).
     Приклад:
      // Поганий приклад (надлишковість у пакеті client та роздуті назви в циклі)
      package client
      
      type ClientService struct{} // Погано: викликатиметься як client.ClientService
      
      func (cs *ClientService) ProcessItems(listOfItemsToProcess []string) {
      	for currentItemIndex := 0; currentItemIndex < len(listOfItemsToProcess); currentItemIndex++ {
      		// ...
      	}
      }
      
      // Гарний приклад (лаконічно та без повторення імені пакета)
      package client
      
      type Service struct{} // Викликається як client.Service
      
      func (s *Service) ProcessItems(items []string) {
      	for i, item := range items {
      		_ = item
      		_ = i
      	}
      }

     Чому важливо: стиль Go цінує мінімалізм і високу швидкість читання; довгі префікси засмічують код і не несуть нової інформації.
     Наслідки недотримання: виникає громіздкий код у стилі Java enterprise, який складно читати в ідіоматичних Go-проектах.
     Вплив на підтримку: менший обсяг коду підвищує його сприйняття під час код-рев'ю.
     3.3.4 Рекомендація: Замінюйте «магічні» константи типізованими перерахуваннями (iota)   
     Використання літералів чисел або рядків безпосередньо у бізнес-логіці («магічні числа») суворо заборонено. Їх необхідно виносити в іменовані константи або перерахування на базі генератора iota.   
     Приклад:
      // Поганий приклад (використання "магічних" чисел та статусів)
      if user.Status == 2 { // Що означає 2?
      	retryTimeout = 86400 // Що означає 86400?
      }
      
      // Гарний приклад (типізовані константи та iota)
      type UserStatus int
      
      const (
      	StatusPending UserStatus = iota
      	StatusActive
      	StatusSuspended
      )
      
      const DayInSeconds = 24 * 60 * 60
      
      if user.Status == StatusSuspended {
      	retryTimeout = DayInSeconds
      }
     
     Чому важливо: константні типи фіксують допустимий діапазон значень і виключають випадкові друкарські помилки.   
     Наслідки недотримання: висока ймовірність помилок розробника при зміні бізнес-правил, втрата змісту коду без читання всієї бази.
     Вплив на підтримку: зміна значення константи в одному місці автоматично актуалізує роботу всієї системи.
     3.4 Коментарі та уникнення надлишковості
     3.4.1 Рекомендація: Коментуйте причину («Чому»), а не дію («Що»)   
     Код сам по собі має пояснювати, що він робить, завдяки зрозумілим іменам змінних і функцій. Коментарі потрібні лише тоді, коли алгоритм розв'язує неочевидну бізнес-проблему, обходить системний баг або містить специфічний оптимізаційний трюк. Зайві коментарі створюють візуальний шум і швидко застарівають.   
     Приклад:
      // Поганий приклад (надлишковий коментар, що просто дублює код)
      // Збільшуємо лічильник на 1
      counter++
      // Закриваємо з'єднання з базою
      db.Close()
      
      // Гарний приклад (пояснення неочевидного контексту бізнес-рішення)
      // Таймаут у 300 мс встановлено через специфіку поведінки платіжного шлюзу 
      // банку в години пікового навантаження (тікет INFRA-402).
      client.Timeout = 300 * time.Millisecond
     
     Чому важливо: коментарі, які повторюють код, дезінформують команду, коли код змінюється, а текст коментаря забувають оновити.   
     Наслідки недотримання: захаращення кодової бази, поява когнітивного шуму та хибних пояснень застарілих ділянок програми.
     Вплив на підтримку: розробники читають лише корисні бізнес-зауваження, заощаджуючи час на рев'ю.
     3.5 Документування коду (Go Doc)
     3.5.1 Рекомендація: Документуйте всі експортовані сутності з назви цієї ж сутності
     Кожен експортований тип, функція, метод або константа повинні мати коментар документації. Цей коментар має починатися саме з назви документованого ідентифікатора і бути повним англійським (або українським) граматичним реченням.
     Приклад:
      // Поганий приклад (коментар не починається з назви та не інформативний)
      // Ця функція шукає користувача
      func FindUser(id string) (*User, error) { /* ... */ }
      
      // Гарний приклад (ідіоматичний формат godoc)
      // FindUser retrieves a user by their unique identifier.
      // It returns an error if the user is not found or the database is unavailable.
      func FindUser(id string) (*User, error) {
      	// ...
      	return nil, nil
      }
     
     Чому важливо: утиліти генерації документації (go doc, pkg.go.dev) зчитують ці коментарі напряму і форматують їх у зручний огляд пакету.
     Наслідки недотримання: утиліти документації показуватимуть нескладні або вирвані з контексту речення.
     Вплив на підтримку: інші розробники можуть користуватися функціоналом бібліотеки прямо через підказки в IDE без необхідності досліджувати вихідний код.
     3.6 Обробка помилок
     3.6.1 Рекомендація: Явно обробляйте помилки як значення та не ігноруйте їх
     У Go помилки не є винятками (exceptions), а звичайними значеннями, що реалізують інтерфейс error і повертаються останнім значенням з функції [1, 3]. Їх необхідно перевіряти одразу після виклику, а ігнорування через порожній ідентифікатор _ є антипатерном.
     Приклад:
      // Поганий приклад (ігнорування помилки)
      data, _ := os.ReadFile("config.json")
      processConfig(data)
      
      // Гарний приклад (явна перевірка та контекстуалізація помилки)
      data, err := os.ReadFile("config.json")
      if err != nil {
      	return fmt.Errorf("failed to read config file: %w", err)
      }
      processConfig(data)
     
     Чому важливо: помилки є штатною частиною виконання програми. Їхня обробка прямо за місцем виникнення усуває приховані падіння.
     Наслідки недотримання: якщо функція повернула помилку, змінні з даними часто мають нульове значення (nil). Подальше звернення до них призведе до паніки (nil pointer dereference) у рантаймі.
     Вплив на підтримку: явний потік обробки помилок робить поведінку системи детермінованою і легко діагностованою за стек-трейсом.
     3.6.2 Рекомендація: Мінімізуйте вкладеність відступів шляхом раннього повернення (Early Return / Guard Clauses)
     «Щасливий шлях» (happy path) виконання функції повинен йти вздовж лівого краю екрана без зайвих рівнів вкладеності. Помилки та виняткові ситуації обробляються першими з негайним виходом через return.
     Приклад:
      // Поганий приклад (глибока вкладеність)
      func SaveUser(u *User) error {
      	if u != nil {
      		if u.Email != "" {
      			err := db.Save(u)
      			if err == nil {
      				return nil
      			} else {
      				return err
      			}
      		} else {
      			return errors.New("empty email")
      		}
      	} else {
      		return errors.New("nil user")
      	}
      }
      
      // Гарний приклад (лінійний код завдяки раннім поверненням)
      func SaveUser(u *User) error {
      	if u == nil {
      		return errors.New("nil user")
      	}
      	if u.Email == "" {
      		return errors.New("empty email")
      	}
      
      	if err := db.Save(u); err != nil {
      		return fmt.Errorf("database error: %w", err)
      	}
      
      	return nil
      }
     
     Чому важливо: зменшує когнітивне навантаження при читанні, дозволяючи сфокусуватися на основному сценарії.
     Наслідки недотримання: виникає «драбина» або «піраміда приреченості» (arrow anti-pattern), коли логіка розповзається вправо за межі екрана.
     Вплив на підтримку: додавання нових умов валідації в лінійному коді відбувається набагато швидше і без ризику заплутатися в парних фігурних дужках.
     3.7 Керування ресурсами та безпека
     3.7.1 Рекомендація: Звільняйте ресурси за допомогою defer одразу після успішної ініціалізації
     Оператор defer відкладає виконання функції до моменту виходу з огортаючої функції. Його слід викликати одразу після перевірки помилки створення ресурсу (файлу, м'ютекса, з'єднання).
     Приклад:
      // Поганий приклад (defer перед перевіркою або забудькувате закриття вручну)
      file, err := os.Open("data.txt")
      defer file.Close() // ПОМИЛКА: якщо err != nil, file дорівнює nil -> panic
      if err != nil {
      	return err
      }
      
      // Гарний приклад (defer викликається лише після err == nil)
      file, err := os.Open("data.txt")
      if err != nil {
      	return fmt.Errorf("cannot open file: %w", err)
      }
      defer file.Close()
     
     Чому важливо: гарантує, що ресурс закриється за будь-якого сценарію виходу з функції (навіть при виникненні наступних помилок чи паніки).
     Наслідки недотримання: викликання file.Close() до перевірки помилки призведе до критичного збою, а відсутність defer часто стає причиною витоку пам'яті чи файлових дескрипторів.
     Вплив на підтримку: забезпечує цілісність ресурсів та стабільність тривалих сервісів під навантаженням.
     3.7.2 Рекомендація: Не використовуйте panic для керування потоком виконання
     Механізм panic призначений виключно для невідворотних критичних помилок (наприклад, пошкоджена конфігурація на етапі старту програми, коли подальше виконання неможливе). Для звичайних помилок передається error.
     Приклад:
      // Поганий приклад (паніка у бізнес-логіці)
      func ParseAge(ageStr string) int {
      	age, err := strconv.Atoi(ageStr)
      	if err != nil {
      		panic("invalid age string") // Падіння всього процесу
      	}
      	return age
      }
      
      // Гарний приклад (повернення помилки)
      func ParseAge(ageStr string) (int, error) {
      	age, err := strconv.Atoi(ageStr)
      	if err != nil {
      		return 0, fmt.Errorf("invalid age %q: %w", ageStr, err)
      	}
      	return age, nil
      }
     
     Чому важливо: необроблена паніка крашить весь додаток, перериваючи роботу паралельних клієнтських запитів у веб-серверах.
     Наслідки недотримання: програма стає нестабільною, а збої –  непередбачуваними.
     Вплив на підтримку: дозволяє викликам на верхніх рівнях контрольовано реагувати на збій (наприклад, повертати HTTP 400 замість падіння бекенду).
     3.8 Кодування на основі тестування (TDD)
     3.8.1 Рекомендація: Використовуйте ідіоматичні табличні тести (Table-Driven Tests)   
     У Go стандартом є організація тестів за допомогою таблиць випадків (table-driven tests). Замість дублювання тестових функцій створюється слайс анонімних структур із тестовими даними (name, input, expected), який ітерується через t.Run().   
     Приклад:
      // Гарний приклад організації Table-Driven Test у файлі math_test.go
      func TestDivide(t *testing.T) {
      	tests := []struct {
      		name        string
      		a, b        float64
      		expected    float64
      		expectError bool
      	}{
      		{name: "regular division", a: 10, b: 2, expected: 5, expectError: false},
      		{name: "division by zero", a: 5, b: 0, expected: 0, expectError: true},
      	}
      
      	for _, tt := range tests {
      		t.Run(tt.name, func(t *testing.T) {
      			result, err := Divide(tt.a, tt.b)
      			if (err != nil) != tt.expectError {
      				t.Fatalf("unexpected error status: %v", err)
      			}
      			if result != tt.expected {
      				t.Errorf("expected %v, got %v", tt.expected, result)
      			}
      		})
      	}
      }
     
     Чому важливо: полегшує покриття крайових випадків (Edge Cases) та підтримує філософію TDD: перед написанням алгоритму додається новий рядок у таблицю перевірок.   
     Наслідки недотримання: дублювання бойлерплейт-коду тестування, пропуск негативних тестів та крайових значень.
     Вплив на підтримку: додавання перевірки нового випадку зводиться до внесення одного рядка в масив без зміни логіки тестів.
     3.9 Інструменти та автоматизація якості коду
     3.9.1 Рекомендація: Автоматизуйте статичний аналіз коду в CI/CD пайплайнах   
     Якість та чистота коду не повинні залежати лише від людської уважності на рев'ю. В екосистемі Go обов'язковим є використання комплексних лінтерів:
     ­ golangci-lint – агрегатор десятків статичних аналізаторів (govet, errcheck, staticcheck, unused тощо), який запускається на етапі CI перед злиттям гілки (Pull Request);   
     ­ Pre-commit hooks – Git-хуки для локального автоматичного запуску gofmt та goimports перед створенням коміту;   
     ­ SonarQube / Codacy – платформи для довготривалого відстеження технічного боргу, дублювання коду та тестового покриття.   
     Чому важливо: повністю виключає потрапляння невідформатованого коду або неопрацьованих помилок у головну гілку розробки.   
     Наслідки недотримання: накопичення прихованих багів (memory leaks, unhandled errors, data races) та марнування часу рецензентів на зауваження щодо стилю.
     Вплив на підтримку: забезпечує прогнозовану високу якість інженерного продукту на будь-якому етапі життєвого циклу проекту. 
     Посилання на відеозапис захисту роботи наведено у додатку А, графічний матеріал доповіді – у додатку Б, а повний лістинг розглянутих фрагментів програмного коду – у додатку В.
